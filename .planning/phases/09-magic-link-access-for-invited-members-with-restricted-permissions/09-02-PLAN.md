<objective>
Build the magic link email sending and token redemption flow.

Purpose: This is the core magic link mechanism. When an organizer creates an invite with an email, the system generates a secure token, stores its SHA-256 hash, and sends a magic link email. Participants click the link, which leads to a frontend page that POSTs to the redemption endpoint. The endpoint atomically consumes the token and returns a participant-scoped JWT.

Output: emailService, magicLink route, updated invite creation flow
</objective>

    - **POST /redeem** (rate limited, no auth required):
      - Extract `{ token }` from request body
      - Validate token exists and is a non-empty string, return 400 if invalid
      - Hash token: `crypto.createHash('sha256').update(token).digest('hex')`
      - Atomically consume token with single query:
        ```sql
        DELETE FROM magic_link_tokens
        WHERE token_hash = $1 AND expires_at > NOW()
        RETURNING invite_id
        ```
      - If no rows returned, return 401 `{ error: "Invalid or expired magic link" }`
      - Look up invite to get event_id and participant_id:
        ```sql
        SELECT i.event_id, i.participant_id, p.name as participant_name, e.name as event_name
        FROM invites i
        JOIN participants p ON i.participant_id = p.id
        JOIN events e ON i.event_id = e.id
        WHERE i.id = $1 AND i.status = 'accepted'
        ```
      - If invite not found or has no participant_id, return 401 `{ error: "Invalid or expired magic link" }`
      - Call `generateParticipantTokens({ participantId, eventId, participantName })`
      - Set refresh token in HttpOnly cookie (same options as auth.ts: httpOnly, secure in prod, sameSite strict, 7-day maxAge, path /api/auth)
      - Return 200 with `{ accessToken, user: { participantId, eventId, participantName, eventName, role: 'participant' } }`

    1. In `apps/api/src/routes/invites.ts`:

    a. Add imports at top:
    ```typescript
    import crypto from "crypto";
    import { sendMagicLinkEmail } from "../services/emailService.js";
    ```

    b. In the `POST /events/:eventId/invites` handler, AFTER the invite is inserted into the database and the response is built, but BEFORE returning the response:

    - Generate a magic link token using nanoid (already imported): `const magicToken = nanoid(48);` (48 chars for extra entropy)
    - Hash the token: `const tokenHash = crypto.createHash('sha256').update(magicToken).digest('hex');`
    - Set expiration to 24 hours: `const tokenExpiresAt = new Date(Date.now() + 24 * 60 * 60 * 1000);`
    - Insert into magic_link_tokens: `INSERT INTO magic_link_tokens (invite_id, token_hash, expires_at) VALUES ($1, $2, $3)` with params `[invite.id, tokenHash, tokenExpiresAt]`
    - Build magic link URL: `const magicLinkUrl = \`${frontendUrl}/magic-link/${magicToken}\`;`
    - If email was provided on the invite, fire-and-forget the email: `if (invite.email) { sendMagicLinkEmail(invite.email, magicLinkUrl, event.name); }`
    - Add `magic_link_url: magicLinkUrl` to the response JSON so the organizer can also copy/share the magic link manually

    c. The magic link generation should NOT be in a transaction with the invite creation. The invite record is the source of truth; the magic link token is supplementary. If token insertion fails, the invite still exists (organizer can regenerate).

    2. Do NOT modify the invite accept flow. Magic links are a separate authentication path from the existing invite code accept flow. The invite must already be in 'accepted' status with a participant_id for the magic link to work (so the participant must first accept via /join/:code, THEN use the magic link for subsequent authentication).

    IMPORTANT DESIGN NOTE: The flow is:
    1. Organizer creates invite (POST /events/:eventId/invites) -> magic link token generated + email sent
    2. Participant clicks join link or magic link
    3. If join link: accepts invite via existing /join/:code flow (creates participant, sets status=accepted)
    4. If magic link: redeems via POST /api/auth/magic-link/redeem -> gets JWT
    5. For magic link to work, the invite MUST already be accepted (participant must exist)

    So the realistic flow is: organizer creates invite with email -> email sent with both join link AND magic link -> participant first joins via join link -> then uses magic link for future authentication.

    ALTERNATIVE simpler approach: When the magic link is redeemed, if the invite is still 'pending', auto-accept it (create participant from invite email as name, set status=accepted). Update the redeem endpoint in magicLink.ts to handle this:
    - If invite status is 'pending': create participant from email, update invite to accepted, then generate tokens
    - If invite status is 'accepted': use existing participant_id

    Implement the ALTERNATIVE approach in the magicLink.ts redeem endpoint from Task 1. The redeem logic should be:
    ```
    1. Consume magic_link_token (DELETE + RETURNING invite_id)
    2. Look up invite by invite_id
    3. If invite.status === 'pending':
       a. Use transaction to create participant (name = email prefix or full email)
       b. Update invite: SET status='accepted', participant_id=$1
       c. Get event name
    4. If invite.status === 'accepted':
       a. Get participant_id from invite
       b. Get participant name and event name
    5. Generate participant tokens
    6. Return JWT
    ```
