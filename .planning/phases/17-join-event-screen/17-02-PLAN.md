    type JoinState = 'loading' | 'preview' | 'joining' | 'success' | 'already-joined' | 'invalid' | 'error';

    - `previewData: InvitePreview | null` — from validate response
    - `joinedEventId: number | null` — set after successful accept

    **On mount effect (validate):**
    1. If `!token`, set state to 'invalid' immediately
    2. Call `invitesApi.validate(token)`
    3. On success: store previewData, set state to 'preview'
    4. On 404 error: set state to 'invalid'
    5. On network error: set state to 'error'
    The validate response now includes `organizerName`, `participantCount`, and `eventDate` directly — no separate API call needed. These fields come from the extended backend validate endpoint (Plan 01).

    **Already-joined check (effect):**
    After validate succeeds AND user is authenticated, check EventsContext:
    ```typescript
    const existingEvent = events.find(e => e.id === String(previewData.eventId));
    if (existingEvent && existingEvent.people?.includes(user.name)) {
      setJoinState('already-joined');
    }
    ```
    This is best-effort — if the event isn't in context yet, proceed to preview (accept is idempotent).

    **Auto-join on auth state change:**
    When the user returns to the join screen after authenticating (via _layout.tsx pending invite redirect), the screen remounts with `session` already set. Detect this: if `session` exists AND `previewData` is loaded AND `joinState === 'preview'`, automatically trigger handleJoin(). Use a `useEffect` watching `[session, previewData, joinState]` — if all three conditions are met, call handleJoin().

    **handleJoin function:**
    1. **Guard against double-call:** If `joinState === 'joining'`, return immediately
    2. Require auth: if `!session || !user`, call `setPendingInviteCode(token)` and `router.push('/sign-in')`, return
    3. Set state to 'joining' (full-screen overlay)
    4. Call `invitesApi.accept(token, user.name, user.email)`
    5. On success: set joinedEventId, call `refreshEvents()`, set state to 'success'
    6. On network error: increment networkAttempts, set inlineError, set state back to 'preview'
    7. On 404 error: set state to 'invalid'

    **Success auto-navigate (effect):**
    When state is 'success' and joinedEventId is set, start a 2-second timer then `router.replace(\`/event-details?id=${joinedEventId}\`)`. CRITICAL: Return a cleanup function that calls `clearTimeout(timer)` to prevent memory leaks if the component unmounts early.

    **IMPORTANT ARCHITECTURE NOTE:** The sign-in and register screens are inside `Stack.Protected guard={!session}`. After `signIn()` succeeds, the session state changes and Stack.Protected will reactively redirect away from these screens. This means `router.replace('/join?token=...')` called AFTER `signIn()` would RACE against the Stack.Protected redirect and may lose.

    The solution: sign-in and register do NOT navigate to /join themselves. They do NOT call `consumePendingInviteCode`. Instead, the pending invite code was already stored by join.tsx (via `setPendingInviteCode`) BEFORE navigating to sign-in. The `_layout.tsx` pending invite redirect effect (from Plan 01) handles the navigation after auth succeeds and Stack.Protected settles.

    However, there is one edge case: if the user navigates to sign-in from join.tsx, then switches to register (or vice versa), the pending code is already stored. No action needed in these screens for the normal flow.

    BUT: if the pending invite code was consumed by _layout.tsx between the time sign-in rendered and auth completed (edge case), we need the code to still be available. Since `setPendingInviteCode` is called in join.tsx BEFORE navigating to sign-in, and `consumePendingInviteCode` is only called in _layout.tsx AFTER session becomes truthy, the timing is correct: store happens before auth, consume happens after auth.

    **What sign-in.tsx and register.tsx actually need:** Nothing changes in the auth flow itself. The pending invite code is managed by join.tsx (store) and _layout.tsx (consume + redirect). Sign-in and register just do their normal job.

    HOWEVER, to make the flow more robust and handle an edge case where a user manually navigates to sign-in (not from join.tsx) while somehow having a stale pending code, we should ensure no stale codes interfere. This is already handled by `consumePendingInviteCode` clearing the value atomically.

    **Minimal changes needed in sign-in.tsx and register.tsx:**

Both screens work fine without changes.

    BUT: the _layout.tsx useEffect watching `session` may fire BEFORE the Stack.Protected redirect completes. To be safe, sign-in and register should NOT do any post-auth navigation — they should let Stack.Protected and _layout.tsx handle everything.
