<task type="auto">
  <name>Task 2: Refactor PUT /api/users/me to patch-style</name>
  <files>apps/api/src/routes/users.ts</files>
  <action>
Replace the existing PUT handler that only accepts `{ name }` with a dynamic patch builder. **Keep the handler wrapped in `asyncHandler()`** — do NOT remove the asyncHandler wrapper.

1. Extract all patchable fields from request body: `name`, `bio`, `interests`, `avatarUrl`, `onboardingComplete`
2. Build dynamic SET clause — only include fields present in the request body (use `'field' in req.body` or `field !== undefined` check):
   - `name`: validate non-empty string, trim it
   - `bio`: accept string or null (null clears to NULL)
   - `interests`: accept array, use `JSON.stringify()` for JSONB insert (full replace)
   - `avatarUrl`: accept string or null (null clears to NULL), maps to `avatar_url` column
   - `onboardingComplete`: ONE-WAY — only accept `true`. If value is `false` or anything non-true, silently skip it (do not add to SET clause, do not error). This is the intentional simplified approach per locked decision: the server rejects ALL false values unconditionally, rather than checking the current DB state. This is acceptable because onboarding is write-once.
3. If no valid fields provided, return 400 `{ error: 'No fields to update' }`
4. Append `updated_at = NOW()` to SET clause
5. Use parameterized query: `UPDATE users SET ${fields.join(', ')} WHERE id = $N RETURNING id, email, name, bio, interests, avatar_url, onboarding_complete, created_at`
6. Map response to camelCase (same shape as GET, preserving createdAt and eventsOrganized):
```typescript
{
  id: u.id, email: u.email, name: u.name,
  bio: u.bio ?? null, interests: u.interests ?? [],
  avatarUrl: u.avatar_url ?? null,
  onboardingComplete: u.onboarding_complete,
  createdAt: u.created_at,
  eventsOrganized: parseInt(eventsResult.rows[0].count, 10) || 0,
}
```
Note: To include `eventsOrganized` in the PUT response, either re-query the events count or simply return the user fields without it (the GET endpoint is the canonical source). Choose whichever matches the current pattern — if the existing PUT returns `eventsOrganized`, keep it; if not, omit it.

Important: Remove the old `name`-only validation. The new handler should NOT require name — it's optional in a patch.
  </action>
